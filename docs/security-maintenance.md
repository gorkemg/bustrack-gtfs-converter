# Security maintenance

The `security-check` job runs the standard-library unit tests on pull requests, pushes to main, daily and on demand. It uses a read-only token and does not publish releases. This is a test suite, not a static vulnerability scanner or a guarantee that feeds are safe. Dependabot checks GitHub Actions daily; there are no Python dependency manifests to monitor. Review proposed action updates and verify the upstream commit before merging. GitHub does not generate action vulnerability alerts for SHA-pinned references; version updates still provide maintenance coverage.

Only main can publish or run rollback: config pushes are filtered to main, the sync job checks the ref, and rollback rejects other refs. The release workflow fails on converter errors and publishes only after checking the generated ZIP's expected single regular entry, size, SQLite integrity, agency metadata, schema version and core table presence and non-emptiness. An explicit unchanged result skips publication. This does not establish provenance or semantic correctness of upstream GTFS data. Release operations are separate GitHub API calls and are not atomic: a later failure may leave an archive or previous release updated without updating production.

Input requests require HTTPS with the standard certificate verification and at most five redirects. GitHub API authorization is restricted to api.github.com on port 443 and never forwarded across origins. Network operations use a 180-second monotonic budget and a 15-second socket timeout, with the remaining budget applied to response reads. OS DNS resolution and slow HTTP response headers are not strictly interruptible by this Python interface, so this is not an absolute hard wall-clock deadline. GTFS downloads are capped at 512 MiB; ZIPs at 1,000 entries, 1 GiB per member and 2 GiB total expanded size. Only stored and deflated ZIP entries are accepted; paths, file types and duplicate flattened GTFS names are checked before staged extraction. Invalid downloads leave the old input untouched. During the final directory swap the old input is kept as a backup in the staging directory; an uncatchable termination between the two renames may require manual restoration of that backup.

PVTA route details now use HTTPS. On 2026-10-28 the TLS-verified GET returned HTTP 200 and 950,026 bytes of JSON: 60 route records, 58 with an abbreviation and 60 with a short name. Both HTTPS feeds were also sampled that day: PVTA 6,457,219 compressed / 46,169,289 expanded bytes; UTA 8,760,119 / 32,981,264 bytes. These observations do not guarantee future availability or data authenticity beyond transport authentication. Route details are capped at 5 MiB, UTF-8 is required, NUL bytes and non-UTF-8 XML declarations are rejected, and DTD/entity declarations are rejected, and only syntactically valid data containing a usable route mapping is cached. A new cache namespace avoids reusing legacy HTTP-fetched content. If the HTTPS service is unavailable, a validated cache is used; without one enrichment falls back to route IDs.

The release check still falls back to downloading when metadata checks fail; source metadata is not an authenticity guarantee. Archive limits do not establish semantic correctness or prevent all resource-exhaustion attacks. Rollback restores a previously published asset and does not revalidate it here.

## Beta monitoring

The default-branch security workflow explicitly checks out beta for a separate read-only beta-security-check on its daily schedule and manual security-check runs. Pull requests continue to use security-check against the proposed branch; they do not publish releases. A schedule in beta alone would not run daily. Both jobs must be inspected when reviewing a scheduled run. Dependabot version-update PRs target the default branch; beta receives deliberate security backports. Test success does not establish feed freshness or semantic correctness.
